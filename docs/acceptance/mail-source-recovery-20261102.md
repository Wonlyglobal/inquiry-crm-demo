# Exact original-mail recovery for historical reminders

The project owner explicitly requested searching the original mailboxes for originals and attachments referenced by 15 already-reviewed reminders, registering only independently confirmed procurement needs, avoiding duplicates and preserving existing values. This is a maintenance review, not an automatic purchasing classifier.

The existing desktop mailbox session covers only the official inquiry account; the exact reminders span five existing connected mailboxes. A dedicated server-only worker uses those existing connections so credentials stay server-side. The private maintenance manifest is seeded separately from the frozen reminders, validated by source hashes, and contains at most 15 reminder IDs and 31 tasks per mailbox. It is not included in Git. No public user-search body, credential response, new user permission or scheduled job is added.

Only the existing dedicated mail-worker token can invoke the POST handler. Service-only, leased RPCs expose approved pending jobs to that worker and append immutable events. Anonymous and ordinary/readonly users cannot claim jobs or read the private tables. Active production accounts and existing download/reveal blocks are checked before credentials or IMAP access. Jobs are bounded, retried at most three times, and distinguish missing, partial, blocked and conflicting sources.

IMAP folders are opened read-only, including Junk/Trash if selectable; Drafts are excluded. Search uses the frozen sender, subject and date window. A fetched original must match the sender and normalized subject, with the header time within 15 minutes of the digest entry. Same-theme mail at another time is not accepted as the original. Message count, folder count, source size, attachment type and size caps remain explicit unresolved outcomes. Attachments and mail content are never executed or sent to external AI. No SMTP or outbound messaging capability is invoked.

Recovered sources are stored only as ignored, unassigned review records under an additional restrictive owner/mailbox-owner policy intersecting original RLS. Existing messages, inquiry associations, bodies and attachments are reused without replacing values; conflicting IDs/UIDs are unresolved. A trigger holds new sources for review until a separately converted intake matches the actual original. The worker never creates or changes inquiries, intake records, contacts, companies, communication summaries, tasks, or pipeline progress. Business registration is a separate authorized review step and must use normal deduplication/conversion.

Before release, run the offline regression and locked mail tests plus `PGLITE_MODULE=/verified/pglite/index.js node scripts/check-mail-source-recovery-rls.mjs`. The PostgreSQL checks use synthetic data only and cover ACL, leasing, source drift, immutable audit, readonly visibility and exact-source conversion. Production completion still requires invoking the approved jobs, reading their results, reviewing originals/attachments, and verifying existing values remain unchanged.

Rollback: stop invoking the dedicated worker and revert its code through normal release controls. Retain original-source evidence, recovered files, private batch/job/events and audits; do not delete history or restore overwritten values because the process does not overwrite them. Revoke only the new job RPC execution if retiring the capability, preserving normal email sync. No existing Secret, cron, mailbox setting or external AI policy needs changing. Provider retention or deleted originals may still prevent recovery and must be reported per entry rather than labelled a non-purchase.
