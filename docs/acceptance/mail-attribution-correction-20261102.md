# System notification attribution correction

The project owner authorized reviewing the 42 mismatched messages on one inquiry, correcting attribution, and registering only independently confirmed procurement requests without duplicating or overwriting existing records. Customer identifiers and operational manifests stay in the private evidence directory and are not committed.

The frozen sources are 25 junk digests, nine delivery failures, four login alerts and four provider notifications. None is itself an independent procurement request. Thirteen indexed originals referenced by the digests were checked separately; two already have inquiries. Test traffic, promotions and incomplete or link-dependent candidates must not be silently converted into new procurement inquiries.

The migration adds an immutable private maintenance journal and a retained-history state to communication, summary and reminder rows. Ordinary communications still require an inquiry; only rows referencing a real correction batch can have no inquiry. Original content, authors, times and reminder states stay intact. Restrictive policies hide retired business attribution even from broad readonly policies. Detached system notifications remain subject to original RLS and an active owner/mailbox-owner restriction. A database trigger prevents the exact corrected sources from being reassociated by re-sync. Definer daily-report and sales-scoring queries explicitly exclude retained correction history, with exact source guards; submitted historical reports are not rewritten.

The mail worker recognizes strong transport/account notices before thread/contact matching and intake creation. A no-reply sender alone does not qualify; genuine website RFQs and human requests remain eligible. The self-contained Edge runtime is generated from the reviewed mail service, with an exact-byte regression check and unchanged token/POST protection and dependency versions.

Validation before production: isolated PostgreSQL tests cover normal inquiry constraints, correction foreign keys, resync protection, immutable journals, normal/readonly role visibility, private access denial, source-content preservation and guarded routing restoration. Run `PGLITE_MODULE=/verified/pglite/index.js node scripts/check-mail-attribution-rls.mjs`; this is a synthetic database only. Full offline regression and locked mail compatibility checks are required. Passing these checks is not evidence of production correction.

Production execution must use the private exact-ID and source-fingerprint manifest in one locked transaction, record truthful database-maintenance provenance with no impersonated user, and verify all existing inquiry/contact/company/source/attachment values remain unchanged. The journal records routing before/after and hashes, not another copy of email bodies. Do not replay historical pipeline notifications or invoke external AI. Deployment and final counts belong in the project delivery logs.

Rollback: revert the worker through the normal release path. Restore routing only after checking the immutable journal, current source hashes and expected correction state; suspend the specific resync guard only in that audited transaction when intentionally restoring a known bad association. Retain all journal and audit rows. Restoring source functions requires matching the released hashes and preserving privileges. No original messages, attachments, inquiries or historical reports are deleted.
